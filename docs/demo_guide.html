2. How a turn works (point at the trace as you say this)

you type → PII screen (masked or clean?) → read recent Redis turns → embed query locally → retrieve top-k Postgres memories (scores shown) → build prompt (memories included — or zero if retrieval off) → ONE hosted call → answer + memory proposals → POLICY GATE per proposal: ADD / SUPERSEDE / REJECT + reason → save turns to Redis → answer + full trace

The one line to land: the model proposes, Python disposes. Retrieval only reads; nothing is stored unless the policy accepts it.

4. Live walkthrough (5 minutes)

Step 1 — a preference. Ask "What tea do I like?" Point at retrieved preference "roast tea" with its similarity score, then at the policy row that accepted or rejected any proposal.
Step 2 — retrieval is similarity, not understanding. Ask "What is Python?" Show the weak scores (~0.4): with a tiny store, top-k returns the least-distant rows even when nothing is truly relevant.
Step 3 — retrieval off. Untick Retrieval, repeat the tea question. The prompt section shows zero durable memories — proof the path is excluded.
Step 4 — Clear vs Forget. Press Clear session: chat empties but roast tea still retrieves (durable ≠ working). Then Forget user: memories, events, and all working sessions for the user are gone.
Step 5 — top-k. Move the slider to 1 and back to 10 on the same question and compare which rows survive. Top-k is simply how many vectors Postgres returns.
