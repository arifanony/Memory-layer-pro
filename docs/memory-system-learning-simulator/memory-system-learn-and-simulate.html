Designing a ChatGPT-Style Memory System

A memory system is not a database. It is a standing decision about which pieces of information are valuable enough to carry into the future, and which ones the system is better off forgetting.

We will build the memory system the way a strong engineer would: start with why it exists, borrow the structure of human memory, turn that into components, then walk every block of the write path, the read path and the background jobs, with real examples and the actual formulas. Part A / Why

Why memory exists, before how it works

Most people ask how to build a memory system. The better question is why it exists at all, because once you can answer that, the architecture becomes almost obvious.

01

Why do we need a memory system?

Imagine ChatGPT without memory. In one conversation you say you like short answers. In the next you ask it to help plan your startup, and it has forgotten everything.

❌ Without memory
Monday
I prefer short answers. And I don't drink coffee.
Got it!
Tuesday · new chat
Suggest a morning drink before my meeting.
Here's a detailed 6-paragraph guide… start with a double espresso! ☕
The user pays the same cost again: re-explaining who they are, what they want, how they like to be spoken to.
✅ With memory
Monday
I prefer short answers. And I don't drink coffee.
Got it!
Tuesday · new chat
Suggest a morning drink before my meeting.
Masala chai. Warm, no coffee.
Short (procedural memory) and no coffee (semantic memory). Nothing had to be repeated.

Without memory, the same costs repeat in every conversation. So memory exists to solve exactly one problem: reducing information loss across interactions.

That single sentence already rules out the most common mistake, which is treating memory as a place to dump everything the user ever said.

Memory is not storage. A database stores everything. A memory system stores only the things that improve future behaviour. Memory is selective retention of information that improves future decisions.

The user says…Will it improve a future decision?Remember?
"I am building SecondBrainLabs."Yes, it anchors many future conversationsKeep
"I use PostgreSQL."Yes, it shapes future technical answersKeep
"I prefer short answers."Yes, it shapes every single replyKeep
"I ate dosa today." / "Today I had coffee."True, but it changes no future decisionForget

Hold on to the word selective. It means the very first thing standing in front of our store is not a write. It is a decision about whether to write at all. That gate is the seed of the whole architecture.

The question we ask

Why does this system exist at all, and what single problem justifies it?

Discuss, then reveal
It removes information loss across conversations. If you cannot name the one loss a system removes, you are designing a feature nobody needs.
Carry into the architectureA write gate. Storage is never the first step. Every candidate memory passes a selection decision first: store only what improves a future decision. It gets its name in section 08 (the Evaluator).
02

How do humans remember?

Before touching vectors, embeddings, databases or RAG, ask how human memory works. When something is genuinely hard, look for a system that already solved it.

Think about your own brain for a moment

🧑‍🤝‍🧑 You don't re-introduce yourself
A close friend doesn't ask your name, your job and your food habits every morning. They carried that information forward.
🚌 You don't keep everything
You remember that you started a new job. You don't remember the colour of a stranger's shirt on the bus this morning.
🗂️ You keep things in different ways
"Went to Kashmir last summer" (an event), "I know Python" (a fact) and "I learn best bottom-up" (a habit) feel different, and they last for different lengths of time.

The key observation: humans don't remember everything, and what they keep is not stored the same way. They remember in kinds, and each kind has a different lifetime, different update rules and different retrieval triggers. That tells us our store should not be one undifferentiated bucket.

The four kinds of memory, and what goes into each

📅 Episodic memory
experiences · time-stamped events
Things that happened, with a when attached.
  • "The user launched a startup."
  • "The user traveled to Kashmir."
  • "The user is going to Bangalore tomorrow for work."
  • "The user had a meeting with the investors on Friday."
Engineering shape: an event log with timestamps, append-only. Fades fastest.
🎯 Semantic memory
stable facts · no timestamp needed
Things that are true across many conversations, rarely changing.
  • "The user knows Python." (skill)
  • "The user works in ML." (role)
  • "The user is building SecondBrainLabs." (project)
  • "The user's students are ML beginners." (relationship)
  • "The user does not drink coffee." (preference fact)
Engineering shape: a fact table you can overwrite when a fact changes; deduplicated.
⚙️ Procedural memory
how the user likes things done
Shapes how we respond, not what we say.
  • "The user prefers bottom-up learning."
  • "The user likes first-principles explanations."
  • "The user prefers short answers."
Engineering shape: a small, high-priority preference set that is almost always worth loading. Doesn't fade.
💭 Working memory
the live context · tiny and volatile
Everything inside the current conversation.
  • The last few messages of this chat.
  • The question being asked right now.
Engineering shape: simply the model's context window. Held for minutes, then gone unless promoted.

Read those four again as an engineer. The taxonomy is not trivia; it is a schema waiting to be written. ChatGPT-style memory is basically an engineering version of cognitive science.

Try it · sort the memories

Click the type you think each sentence belongs to. You get instant feedback.

The promotion path

Working (minutes)→ useful in this session →Session (days–weeks)→ recurs across sessions →Long-term (months–years)

A fact mentioned once in working memory, if it proves useful, gets promoted to a longer-lived kind so it survives the conversation. That promotion is the write gate from section 01, now with a direction.

The question we ask

Is there a mature system, natural or engineered, that already solved a version of this problem, and what structure can I borrow from it?

Discuss, then reveal
Analogies hand you a ready-made decomposition. Caches borrow from working memory, ledgers from accounting, recommendation from word of mouth.
Carry into the architectureA typed memory taxonomy. episodic events, append-only · semantic facts, overwritable, deduplicated · procedural preferences, small set, high retrieval priority · working the live context window, not persisted by default.

Part B / Turning it into a system

How do we make an agent remember like that?

Now we translate the human idea into components, the data that flows between them, and the places it is stored.

03

The job of memory, and the components that do it

Step 1 · Map the mess

Without memory, the same costs repeat on every conversation:

EventProblem
User repeats a preferenceWaste
User repeats goalsWaste
User repeats project contextWaste
User repeats constraintsWaste

The trigger is a message arriving. The output is relevant historical context appearing. The human thinking required is none: the work is entirely mechanical, which is exactly what makes it automatable.

Step 2 · Break memory into parts

⚡ Trigger
Fires when a message arrives.
🔍 Extractor
An LLM task that reads the conversation and finds preferences, goals, projects, relationships and long-term facts.
⚖️ Classifier / Evaluator
Decides whether something is worth remembering. Remember "building SecondBrainLabs"; don't remember "ate dosa today".
🗄️ Memory store
The database where approved memories live.
🧭 Retriever
Searches for the memories relevant to the new message.
🧩 Context composer → LLM
Assembles the package; the response generator uses it to answer.

Step 3 · Two pipelines

Write path · after the replyMessage → Extractor → Classifier → Store. It decides what to keep. In the real system it runs in the background, so the user never waits for the system to "take notes".
Read path · before the replyNew message → Retriever → Context builder → LLM. It decides what to recall. It runs while the user waits, so it must be fast (target under 100 ms).
The question we ask

What are the components, what flows between them, and what is the shape of the data each one hands to the next?

Discuss, then reveal
A system is components plus the contract between them. Name the boxes, then name the object that travels along the arrows. The object (here, the memory record in section 06) is usually more important than the boxes.
Carry into the architectureWrite path: Trigger → Extractor → Classifier → Store · Read path: Retriever → Context Composer → Response LLM
04

Industry-standard thinking: six subsystems

Most beginners picture one arrow: user → vector database → retrieve. That is not how production systems work, and the gap between those two pictures is the gap between a demo and a product. A modern memory system is six separate subsystems, each with its own job and its own failure modes.

SubsystemIts one jobThe question it answersWhere you'll meet it
CaptureTurn raw conversation into candidate memoriesWhat did the user just reveal?§07 Extractor
StoragePersist memories durably and by typeWhere does this live, how is it indexed?§05, §06, §10
RetrievalFind the memories relevant to the momentGiven this query, what matters?§11, §12
EvaluationDecide what is worth keeping and how good retrieval wasIs this useful, and is it working?§08 Evaluator
DecayLet unused memories fade and archiveWhat should be forgotten?§14
GovernanceControl what may be remembered, deleted, inspectedWhat may we keep, can the user see it?§08 PII filter, §17 planes

When someone says "design a memory system", you don't start naming databases. You name these six boxes, say which is hardest (almost always retrieval and evaluation), and go deep there. Collapsing all six into "a vector store" hides four of the six problems.

Carry into the architectureSix subsystems as the top-level boundaries: Capture, Storage, Retrieval, Evaluation, Decay, Governance. Every block we add will slot into one of them.
05

Four storage layers: where memories live, and for how long

The taxonomy in section 02 was by kind. This one is by lifetime. Kind tells us how to store a memory; lifetime tells us where and for how long. Each layer has a different read frequency and a different cost, so they are kept separate.

LayerLifetimeHoldsWhere it lives
Working memoryMinutesThe current conversationContext window
Session memoryDays to weeksThe current project: SBL, the ML course, the Agentic SWE KitFast cache, e.g. Redis
Long-term memoryMonths to yearsPrefers first-principles learning, runs a startup, likes detailDurable store, Postgres
Knowledge memoryReferenceExternal, non-personal documents: PDFs, course materials, papersVector index, RAG

The routing rule for writes

  1. A new fact enters working memory for free.
  2. If it proves useful within the session, it is promoted to session memory.
  3. If it recurs across sessions, it graduates to long-term memory.
  4. Uploaded documents skip the personal layers and go straight to knowledge memory.
In the simulator: why two chat tabs share memoryEach chat tab has its own session in Redis (usr_771:session:chat_A, …chat_B), so the conversations stay separate. But both read the same long-term memory in Postgres, which is stored per user. That's why a fact told in chat A is recalled in chat B.
The question we ask

Should things that live for minutes really sit in the same store as things that live for years?

Discuss, then reveal
No. Mixing hot, short-lived data with cold, long-lived data in one store is how systems get slow and expensive at the same time.
Carry into the architectureFour tiers plus a promotion rule: working in the context window, session in a cache, long-term in Postgres, knowledge in a vector index. working → session → long-term, documents straight to knowledge.
06

How one memory is stored: the memory record

When the extractor reads a message and the evaluator approves it, what lands in the store is a structured record, not a blob of text. Deciding its fields now is what lets every later block (ranking, decay, governance, explainability) do its job. Each field earns its place by enabling a future decision.

-- the memories table (PostgreSQL + pgvector)
create extension if not exists vector;
create table memories (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null,
  type          text check (type in ('episodic','semantic','procedural')),
  content       text not null,
  embedding     vector(1536),
  importance    int,            -- set by the evaluator
  confidence    real,           -- how sure we are it is true
  source        jsonb,          -- provenance: conversation, message, time
  weight        real default 1.0,
  reinforcement int  default 0,
  archived      boolean default false,
  created_at    timestamptz default now(),
  updated_at    timestamptz default now()
);
create index on memories using ivfflat (embedding vector_cosine_ops);
alter table memories enable row level security;   -- invariant 1

Every field explained, with a real row

Example: the user said "I don't drink coffee" in conversation 42.

Two fields quietly do strategic work. importance and confidence let the system tell "the user is building SecondBrainLabs" apart from "the user is maybe thinking about moving cities". source lets the system later answer why do you think that?

Alongside the row: two more structuresA keyword index on content (Postgres full-text search) for exact-word matches, and an edges table (from_id, to_id, relation) for the graph, e.g. User —DISLIKES→ Coffee. Both feed hybrid retrieval in section 11.

The life of one memory

A memory is not just stored. It is born, lives, changes and dies, and every stage is designed:

StageExample: "where the user lives"
Create"User is exploring a move to Bangalore" is created with low confidence.
Update / mergeWeeks later "User now lives in Bangalore" arrives. The two are merged, confidence rises.
ArchiveThe old wording is archived but kept for provenance.
DeleteA year later the user says "forget where I live", and it is deleted for good.
Carry into the architectureThe memory record, with importance, confidence and source as load-bearing fields, plus weight and reinforcement for decay, and a lifecycle of create · update · merge · archive · delete.

Part C / Write path, block by block

Deciding what to remember

The write path runs after the reply, in the background: Gateway → Extractor → Evaluator → Conflict resolver → Write service → Store.

07

Block 1–2 · Gateway and Extractor

Gateway: the single front door

It checks who the user is (authentication) and routes the message. "Gateway" just means one guarded entrance instead of many. It tags every message with the user's id, so every later step works only on that user's memories, and it sends the message down both paths: the read path now, the write path afterwards.

Takes inA chat message
Hands outThe message, tagged with user_id, sent to both paths

Extractor: what did the user just reveal?

An LLM reads one conversation turn and pulls out candidate facts: preferences, goals, projects, relationships, long-term facts. Each candidate is rewritten as a short, standalone sentence and labelled with its type.

// input: one user turn
"I'm vegetarian, and I'm flying to Bangalore tomorrow for a client visit."

// output: candidate memories as JSON
[
  { "type": "semantic", "content": "User is vegetarian" },
  { "type": "episodic", "content": "User is flying to Bangalore tomorrow for a client visit" }
]
Human analogyListening to a friend, you don't memorise their exact sentence. You note the point: "she's vegetarian", "he's travelling tomorrow".

The extractor only proposes. It never writes to the store. Whether a candidate is kept is the evaluator's decision.

08

Block 3 · The Evaluator: importance, confidence and the write gate

This is where most memory systems fail. The naive system stores everything, which creates memory pollution: a store so full of noise that retrieval drowns and every context is cluttered with irrelevant facts.

Instead of storing by default, the evaluator scores each candidate by future utility, asking one question: will this improve a future conversation?

utility high
"I use PostgreSQL"
A stable fact that will shape future technical answers. Store it.
utility high
"I am building SecondBrainLabs"
A project that anchors many future conversations. Store it, high importance.
utility low
"Today I had coffee"
True, but it changes no future decision. Discard it.

The two scores the evaluator sets

⭐ Importance (1–10)
How much will this help future answers?
  • 8–10: projects, core facts, strong preferences ("building SecondBrainLabs")
  • 5–7: useful facts and plans ("doesn't drink coffee" = 7, "going to Bangalore tomorrow" = 6)
  • 1–3: trivia ("ate dosa today" = 2)
Later used as one of the four ranking signals, and as "armour" against decay.
🎯 Confidence (0–1)
How sure are we that this is true, and that the user meant it?
  • "I don't drink coffee." → 0.98 (clear, direct)
  • "I'm thinking of maybe moving to Bangalore." → low (a thought, not a fact)
  • "I live in Bangalore now." → high
Protects against wrong memories, and decides who wins when two memories conflict (section 09).
Why confidence matters: the "wrong memory" failure"Thinking of moving to Bangalore" stored as "lives in Bangalore" is worse than storing nothing: the assistant will now confidently get it wrong. The fix is a confidence score and verification.

Plus a security check: the PII / secret filter

Before anything is written, a filter (for example Microsoft Presidio) scans each candidate and blocks passwords, card numbers and secrets. Example: the user pastes an API key mid-conversation; the filter catches it and the evaluator drops it, so it never reaches the store.

The write-gate rule

BLOCK  if the candidate contains a secret / PII
DROP   if importance < 4   OR   confidence < 0.60
KEEP   otherwise → save with (type, importance, confidence)

In an MVP the evaluator can be an LLM judge prompted with "should this memory improve future conversations? yes/no, importance 1–10". At scale it becomes a cheap deterministic classifier, because the same memory must score the same way every time.

Try it · put messages through the write gate

Click a message. Each stage of the gate shows pass or fail, then the final verdict.

A good memory system is mostly a forgetting system. The hard engineering is not in what you keep; it is in what you have the discipline to throw away.

Carry into the architectureThe Evaluator, between Extractor and Store. It scores future utility, sets importance and confidence, runs the PII filter and drops low-value candidates. This is the named write gate.
09

Block 4 · Conflict resolution: when people change their minds

When a new memory contradicts an old one, the system must decide which is true now. It must not simply keep both and confuse itself, and it must not store the same fact twice.

Example from the study: old memory "works in EdTech", new memory "runs a B2B SaaS". Three possibilities:

PossibilityWhat to do
It's a real changeUpdate: the new one becomes current, the old one is archived
Both are trueKeep both
One is a mistakeKeep the higher-confidence one

A simple rule: newer and higher-confidence usually wins, but always keep the old one's provenance so the change is auditable.

How it works in our architecture

Before committing, the new candidate is compared with existing memories on the same subject using embedding similarity (1 = same meaning, 0 = unrelated). Three actions:

ActionWhenExampleEffect in Postgres
REINFORCE (no-op)Similarity ≥ 0.82, same meaningStored "doesn't drink coffee" · new "I never drink coffee"No new row; existing reinforcement + 1
SUPERSEDESimilarity ≥ 0.82, contradictionStored "doesn't drink coffee" · new "switched to espresso" (similarity 0.89)Old row archived, pointing to the new one; new row inserted
INSERTSimilarity < 0.82, unrelatedStored "doesn't drink coffee" · new "I'm vegetarian"New row added
Human analogyWhen a friend moves from Mumbai to Bangalore, you don't think they live in both cities. You update "lives in" to Bangalore, and you still remember they used to live in Mumbai. That's SUPERSEDE plus archive.
Check yourself

Stored "works at Infosys". New: "I joined TCS last week." Which action?

Reveal
SUPERSEDE. Same subject (employer), opposite value, high confidence. Archive "works at Infosys" (keep provenance) and insert "works at TCS".
10

Block 5 · Write service and indexes

The write service takes the approved record, creates its embedding, and writes it to the right tier, together with the indexes that make it findable later:

🧭 Vector index
The embedding column with an ivfflat index, for meaning search (pgvector).
🔤 Keyword index
Postgres full-text search on content, for exact words: names, versions, prices.
🔗 Graph edge
A row in the edges table: User —DISLIKES→ Coffee, User —TRAVELING_TO→ Bangalore.
Why Postgres + pgvector, not a separate vector databaseOne database is simpler to run, simpler to back up, and keeps structured and semantic memory in one row. pgvector is an extension inside Postgres, not a separate system. A dedicated vector cluster is added later, only if retrieval volume forces it.
Security at write timeTenant isolation: every query carries WHERE user_id = …, enforced by Postgres row-level security, so a forgotten filter can't leak data. Encryption at rest with keys in a key manager (AWS KMS / HashiCorp Vault).

Part D / Read path, block by block

Recalling the right memories, fast

People optimise storage; professionals optimise retrieval. The user only ever experiences what you surface, never what you kept.

11

Block 6 · The Retriever: hybrid search (semantic + lexical + graph)

Pure embedding search misses exact facts (a name, a version number, a price). So production retrieval is hybrid: it searches three ways at once, because each method catches what the others miss.

🧭 Semantic (vector)
finds MEANING
Turns the query into an embedding and finds memories with similar meaning, even with different words.

"morning drink" finds "doesn't drink coffee".
🔤 Lexical (keyword)
finds EXACT STRINGS
Matches the literal words. Catches names, versions and codes that meaning search blurs.

"pgvector" or "Bangalore" matched exactly.
🔗 Graph
finds RELATED THINGS
Walks relationships between entities instead of guessing by similarity.

user → SecondBrainLabs → pricing.

Worked example from the study

Query: "What database does the user use?"

MethodWhat it surfaces
Vector"prefers relational databases"
Keywordthe literal "pgvector"
Graphuser → project → tech stack

Three weak signals combine into one strong answer.

How the three are fused into one "hybrid similarity"

S_hybrid = 0.65 × S_semantic  +  0.25 × S_lexical  +  0.10 × S_graph
// each part is between 0 and 1; meaning carries most of the weight
Exactly what the simulator computesQuery "morning drink in Bangalore?" vs. the memory "does not drink coffee": semantic 0.92, lexical 0.45, graph 0.85 → S_hybrid = 0.65×0.92 + 0.25×0.45 + 0.10×0.85 = 0.598 + 0.113 + 0.085 = 0.80.
The failure this fixes: retrieval missThe memory exists but is never retrieved, because pure vector search didn't match the exact name. Hybrid retrieval is the fix.
ReliabilityIf the memory database doesn't answer within 150 ms, a circuit breaker returns an empty list and the assistant still answers, just without personalisation. Retrieval failure must never block a response.
12

Block 7 · Ranking: how the retrieval score is calculated

When the user says "help me design a course", not all memories matter, and pulling the wrong ones is as bad as pulling none. Which belong in context?

MemoryWhy it scores high or low
User prefers first-principles teachingHigh. Procedural, directly shapes the answer.
User's students are ML beginnersHigh. Defines the audience for the course.
User is running an ML course projectHigh. Same project, recent, reinforced.
User uses PostgreSQLLow. True, but irrelevant to course design.
User traveled to KashmirLow. Episodic, no bearing on the task.

To make that judgement automatically, score every candidate across several signals and take the top-k.

The formula

Final Score = 0.4 × Semantic relevance   (S_hybrid from section 11)
            + 0.2 × Recency
            + 0.2 × Frequency
            + 0.2 × Importance
then retrieve top-k

Each signal, exactly as the simulator computes it

SignalMeaningFormulaIntuition
Relevance (0.4)How well the memory matches this queryS_hybrid = 0.65·sem + 0.25·lex + 0.10·graphCarries the most weight: an irrelevant memory should never win
Recency (0.2)Newer or recently used memories weigh moreR = e^(−λ·days since last used)
λ = 0.25 episodic, 0.04 others		Events go stale quickly; facts don't
Frequency (0.2)Mentioned or used repeatedly, so likely durableF = min(1, ln(1+uses) / ln(11))Grows fast at first, reaches 1.0 at 10 uses
Importance (0.2)Set by the evaluator, scaled by how alive it isI = (importance/10) × weightA faded memory counts less

The study also lists project relevance (belongs to the active project) as a signal. In this design it enters through the graph part of relevance (user → active project).

The usage rewardEvery memory that makes the top-k gets rewarded: reinforcement + 1, its "last used" clock resets, and weight = min(1, weight + 0.15 × (1 + 0.2·ln(reinforcement + 1))). Useful memories keep themselves alive (section 14).
The question we ask

Given a specific request, which subset of everything we know actually matters, and how do we rank it so the best rises to the top?

Discuss, then reveal
Relevance is a scoring problem, not a lookup. Name your signals, weight them, and make the weights tunable. Search, feeds and recommendation are all the same move.
Carry into the architectureA Ranking service over hybrid retrieval. Retrieval fans out across vector, keyword and graph; ranking fuses the signals with tunable weights and returns top-k.
13

Block 8–9 · Context composer and Response LLM

The context composer turns the top memories into a short profile block of text the model reads. The response LLM writes the answer, now personalised.

// what the composer hands to the LLM (≤ 350 tokens of memory)
<user_memory_profile>
  procedural: prefers short answers; first-principles explanations
  semantic:   does not drink coffee
  episodic:   traveling to Bangalore (today)
</user_memory_profile>
<recent_turns> …last turns of this chat (from the session cache)… </recent_turns>
User: Where should I grab a morning drink when I land?

The prompt is built in a fixed order: stable at the top, changing at the bottom

1 · System rulesnever changes · cached
2 · Procedural profilerarely changes · cached
3 · Recent turns of this chat (session cache)grows by one turn · mostly cached
4 · Retrieved memories (≤ 350 tokens)new every message
5 · The user's new questionnew every message

Why? The model can reuse work for the part of the prompt that is identical to last time (prefix caching). Changing parts at the bottom means faster, cheaper answers. And why only ~350 tokens of memory? Because every injected token is paid on every message, and long mixed context makes answers worse. The ranker's job is to make a few memories enough.

Human analogyBefore a meeting you don't re-read your whole diary. You glance at a sticky note with the three points that matter for this meeting.

Part E / Over time

Forgetting on purpose

Human memory fades, and the system should too, for the same reason: a memory that is never used is probably no longer true or no longer relevant.

14

Decay and reinforcement

Each memory carries a weight that erodes over time unless something reinforces it.

weight = importance × recency × reinforcement

Reinforcement is the interesting term. Every time a memory is retrieved and actually helps, its weight is topped up, so useful memories stay alive and stale ones sink on their own.

Example from the studyA user mentioned wanting to learn Kubernetes eighteen months ago and never again. The weight decays, and eventually the memory is archived rather than surfaced into every context. Archived, not deleted, because the user might still ask about it, and provenance must survive.

Mechanically this is a background job, not something on the request path: nightly, multiply weights by a decay factor and archive anything below a floor. This keeps the store from exploding and keeps retrieval fast.

The exact nightly rule in our architecture (2:00 AM)

for every memory that was NOT used today:
   armour     = (importance / 10) × (1 + 0.5 × ln(reinforcement + 1))
   new weight = old weight × e^( −λ / armour )
   if new weight < 0.12  →  archived  (hidden from search, kept for provenance)

λ episodic = 0.08   fades fast
λ semantic = 0.005  almost never
λ procedural = 0    never

if episodic AND reinforcement ≥ 5  →  promoted to semantic (weight reset to 1.0)

Look at the armour: importance and reinforcement sit in the denominator, so the more important or more used a memory is, the less it loses each night.

The question we ask

What should happen to this piece of state over time if nothing ever touches it again?

Discuss, then reveal
State without a decay or expiry policy grows without bound: caches, sessions, feature flags, memories. Design the forgetting at the same time as the remembering.
Carry into the architectureA background decay job and two fields, weight and reinforcement. A nightly worker decays weights and archives below a floor. This is the entire Decay subsystem, off the request path.
15

Reflection agent and memory compression

🪞 Reflection agent: improves quality
A background worker that re-reads many raw memories and rewrites them into fewer, cleaner ones. The system tidying its own notes.

Example: "uses Postgres", "uses pgvector", "deploys with Docker" → one memory: "the user runs a Postgres and Docker stack".

In our architecture it also promotes an episodic memory used 5+ times into a permanent semantic fact.
🗜️ Compression: reduces volume and cost
Replace a hundred detailed memories with ten summaries, to save storage and, more importantly, room in the context window.

Example: fifty small facts about the user's course become one paragraph profile. The originals are archived; the summary is what gets loaded.

This is the fix for the memory explosion failure.

Both run off the request path, like decay. In the assembled architecture they sit in the Background row.

Follow one memory through the whole system

  1. Capture. The user types "I prefer short answers." The extractor emits {type: procedural, content: "prefers short answers"}.
  2. Evaluation. The evaluator says keep, importance 8, confidence high, no PII.
  3. Conflict check. Nothing similar exists → INSERT.
  4. Storage. The write service stores the row and its embedding in Postgres.
  5. Days later, retrieval. The user asks a question. The retriever pulls this memory plus a few others.
  6. Ranking. It ranks near the top; it gets a usage reward (reinforcement + 1, weight up).
  7. Context. The composer turns it into a line the model reads, and the answer comes back short.
  8. Decay. Being procedural, it never decays. An episodic memory would fade nightly unless used.
  9. Feedback. If the user says "actually, be detailed", the conflict resolver supersedes it.

That single trip touches every block. The observability plane logged each hop.
